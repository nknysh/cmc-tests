# cmc-tests

Automated API, contract, performance and end-to-end tests for [CoinMarketCap](https://coinmarketcap.com), written in TypeScript with Playwright and k6. Results from every run are reported to Allure and published on GitHub Pages.

## CoinBoard demo app

[CoinBoard](https://nknysh.github.io/cmc-tests/app/) is a small React app showing the top 100 coins from CoinMarketCap, built as a target for Playwright UI tests. It covers a market table with search, sorting, filters, paging and CSV export; coin detail pages with a price chart; and a converter, coin comparison, watchlist and portfolio. A daily workflow fetches one `listings/latest` snapshot (1 API credit) and publishes it as static JSON, so the API key never reaches the browser. Run it locally with `cd app && npm install && npm run dev`; it uses committed fixture data, so no key is needed.

CoinBoard is developed in four steps, each building on the one before:

1. **User story.** Each feature starts as a story with numbered acceptance criteria, in [`app/user-stories/`](app/user-stories/README.md). When a story describes behavior the app doesn't have yet, it lists it under "Known gaps", and open questions are recorded until someone decides them.
2. **Code.** The app in [`app/src/`](app/src) implements the stories. A change in behavior updates its story first.
3. **Test cases.** A story's test cases go in a `.test.md` file next to it, written for automation. Each case gives its preconditions, the exact data it uses and steps with checkable expected results, and covers named acceptance criteria.
4. **Autotests.** Each `.test.md` file becomes a Playwright spec in [`tests/coinboard/specs/`](tests/coinboard/specs), one test per case, with the same titles and severities.

For example, the Compare stories (`CMP-01` to `CMP-03`) have test cases, and `CMP-01` is automated as [`CMP-01-two-coins-can-be-compared.spec.ts`](tests/coinboard/specs/CMP-01-two-coins-can-be-compared.spec.ts).

### CoinBoard UI tests

The specs in `tests/coinboard/` run in their own Playwright project, `coinboard`:

- **Data:** every test serves the committed snapshot (or a stub built from it) as the app's data, so results don't depend on the live market.
- **Browser errors:** a test fails if the app throws an uncaught error or logs a `console.error`, even when every assertion passed. The errors are attached to the report.
- **Dev server:** any run that includes the project starts the app's Vite dev server. To test a running or deployed app instead, set `COINBOARD_URL`.
- **CI:** the [CoinBoard UI Tests workflow](.github/workflows/coinboard-tests.yml) runs the whole project on pushes and pull requests that change the app or its tests. It publishes the Allure report on every run except pull requests.

Reports are regenerated by the CI workflows and served from the `gh-pages` branch. Each suite keeps its own run history (`allure-history/<suite>.jsonl` on that branch), so each report shows trends across its own runs only and never includes another suite's results.

Each suite also has an Allure quality gate (`allurerc.mjs`). It fails the run on any failed blocker or critical test, or on more than two failures among lower-severity tests. It also fails when the suite has fewer tests than it currently does, so a spec that silently drops out is caught. Every test declares its Allure severity (`tests/helpers/severity.ts`), so the reports can be filtered and grouped by it.

## Technologies

**Language and runtime**
- TypeScript (`typescript` is aliased to `@typescript/typescript6`; TypeScript 7 is installed alongside)
- Node.js 24+

**Testing**
- [Playwright Test](https://playwright.dev) for API specs (no browser) and browser E2E specs (Desktop Chrome)
- UI tests for the CoinBoard demo app, with stubbed snapshot data and a check that fails tests on browser errors
- Contract tests with [zod](https://zod.dev) schemas: live provider checks against the CoinMarketCap API, and offline consumer checks of the client against recorded fixtures
- [k6](https://grafana.com/docs/k6/) latency baseline for the CoinMarketCap API (not a load test: the Basic key allows 30 requests a minute)
- Page Object Model for E2E tests
- Typed HTTP clients for third-party APIs (CoinMarketCap client in `src/clients/`)

**Reporting**
- [Allure Report 3](https://allurereport.org) (`allure`) with `allure-playwright`
- Playwright HTML reporter and list reporter
- GitHub Pages for hosting reports

**Code quality**
- ESLint with typescript-eslint and eslint-plugin-playwright
- Husky pre-commit hook running lint and an AI code review (`claude -p` with the `typescript-code-review` skill)
- SonarQube Cloud static analysis on every push to `main` and every PR, failing the check when the quality gate fails

**CI/CD**
- GitHub Actions: scheduled and manually triggered workflows for API and contract tests, the k6 performance baseline, the BTC price window, and navigation E2E
- GitHub Actions: CoinBoard UI tests on every push and pull request that touches the app or its tests, and a daily CoinBoard deploy

**Self-healing agents**
- BTC price window: recentres the expected price range when the live price drifts outside it, after checks in code (positive price, unchanged width, a shift of at most 10%)
- Navigation locators: repairs the homepage page object using a local LLM (Qwen2.5-Coder-7B-Instruct GGUF via `node-llama-cpp`, no external API)
- Navigation targets: when a tab still works but now leads to a different page, reports the expected and actual URLs and opens a PR updating the test, for a human to review

**AI tooling**
- Claude Code with project skills (`api-testing`, `e2e-testing`) and the Playwright MCP server (`@playwright/mcp`)

**Other**
- `dotenv` for environment configuration

## Setup

```bash
npm install
npx playwright install chromium
npm install --prefix app   # CoinBoard app dependencies, needed to run the CoinBoard UI tests
cp .env.example .env   # then set CMC_API_KEY (CoinMarketCap Pro API key)
```

## Commands

```bash
npm test                # all specs
npm run test:api        # API specs (simple price, quotes latest)
npm run test:contract   # contract specs (provider specs need CMC_API_KEY)
npm run test:btc-price  # BTC price window spec
npm run test:e2e        # browser E2E specs
npm run test:coinboard  # CoinBoard UI specs (starts the app's dev server)
npm run test:perf       # k6 latency baseline (needs the k6 binary and CMC_API_KEY exported)
npm run test:ui         # Playwright UI mode
npm run test:headed     # headed browser

npm run test:allure       # run each Playwright suite, then build its own Allure report
npm run allure:api        # build allure-report/api/ from allure-results/api/
npm run allure:contract   # build allure-report/contract/
npm run allure:btc-price  # build allure-report/btc-price/
npm run allure:navigation # build allure-report/navigation/
npm run allure:coinboard  # build allure-report/coinboard/
npm run allure:perf       # build allure-report/perf/
ALLURE_SUITE=api npm run allure:open  # open one suite's report
ALLURE_SUITE=api npm run allure:gate  # check one suite's results against its quality gate

npm run lint            # ESLint
npx tsc --noEmit        # type-check
```

## Test case viewer

A read-only web UI for browsing the test cases database (`data/test-cases.db`): a collapsible suite tree, the tests in each suite, and a detail view for each test case (description, preconditions, steps). Suites and test cases are shown with their IDs (`#<id> <name>`), and test cases without a suite appear under "Unsorted".

```bash
npm install     # first time only
npm run viewer  # then open http://127.0.0.1:4000
```

Stop it with `Ctrl+C`. The server only listens on `127.0.0.1`. Restart it after editing `index.html`, since the page is read once at startup.

| Env var | Default | Purpose |
|---|---|---|
| `PORT` | `4000` | Port to listen on |
| `TEST_CASES_DB` | `data/test-cases.db` | Path to the SQLite database file |

Test case URLs are shareable, e.g. `http://127.0.0.1:4000/#case/2` (also `#suite/<id>` and `#unsorted`).

- **Skills** (`api-testing`, `e2e-testing`, `test-design`, `typescript-code-review`) are conventions Claude Code loads for a matching task — the first three during interactive development, the last one only inside the headless review invoked by the pre-commit hook.
- **Hooks**: the Husky `pre-commit` hook is the only one wired into `git commit` directly; it runs lint then `PreCommitCodeReviewHook.mts`, which blocks on 🔴 critical findings from the `typescript-code-review` skill. Both self-heal agents deliberately bypass it (`--no-verify`) since they avoid the paid `claude -p` call this hook makes.
- **Agents**: the BTC price window heal runs on every Playwright run via `globalSetup`, including its own and the API-tests cron workflows. Its recentring is gated by checks in code; it used to go through the local-model auditor, which got the arithmetic wrong and blocked valid recentrings. The navigation heal (its own daily cron) has two paths:
  - A broken locator gets a local-LLM patch, verified by re-running the suite, then audited by `auditChange.mts` before committing. Patch generation and the audit both call the same `localModel.mts` helper, which drives the shared, gitignored, locally-cached GGUF model.
  - A tab that now leads to a different page is fixed without the LLM: the script updates the test's expected path, re-runs those tests against the live site and opens a PR instead of committing, because the change edits an assertion. The run stays red until the PR is merged.
